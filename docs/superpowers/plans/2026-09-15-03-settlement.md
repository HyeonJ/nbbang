**Goal:** v1 완성 — 이벤트 비용을 엔빵해 "누가 누구에게 얼마"를 뽑고, 로그인 없는 공개 장부 링크로 투명성을 완성하고, CSV로 내보낸다 (F4·F5·F6·F7 완결).

**Architecture:** 정산은 **선결제자 1명** 모델이다 — 한 사람이 총액을 먼저 내고 나머지가 그에게 보낸다(v1 범위: "회식비 엔빵"). 채권자가 한 명이므로 상계할 것이 없고 이체는 최대 n−1건이다. **여러 명이 나눠 낸 정산(다중 채권자 상계)은 v1 범위 밖** — 그때만 그리디 netting이 필요해진다. 계산은 `lib/domain/settlement.ts`의 순수 함수가 하고, 결과는 `settlement_participants`(참여자별 부담액 + **그 시점의 표시 이름**)와 `settlement_transfers`(누가→누구에게 얼마)에 **완전한 스냅샷으로 저장**한다 — 이름이 바뀌거나 멤버가 떠나도 과거 정산은 변하지 않아야 하므로 현재 명단을 조인해 렌더하지 않는다. 정산은 원장을 건드리지 않는다(모임 돈이 아니라 멤버 간 채무 정리이므로 — ADR-003). 공개 장부는 `publicToken`으로 인증 없이 읽는 라우트이며, 캐시 금지·리퍼러 차단·전용 쿼리(컬럼 명시 선택)로 토큰·개인정보 유출 경로를 모두 닫는다.

**Tech Stack:** Plan 02와 동일 + `drizzle-kit generate/migrate`(마이그레이션 전환), Vitest 통합 테스트(test 브랜치 대상).

- [ ] **Step 2: 세 브랜치는 이미 이 스키마를 갖고 있으므로 "적용됨"으로 표시** — `drizzle-kit migrate`는 `__drizzle_migrations` 테이블로 이력을 관리한다. 기존 DB에 baseline을 그냥 적용하면 `CREATE TABLE`이 충돌한다. 세 브랜치 각각에 대해 **마이그레이션을 실행하지 않고 이력만 기록**해야 한다. drizzle-kit에 전용 명령이 없으므로 스크립트로 처리한다 — `scripts/mark-migration-applied.mts`:
```ts
import { neon } from '@neondatabase/serverless';
import { readFileSync, readdirSync } from 'node:fs';
import { createHash } from 'node:crypto';

// drizzle-kit migrate는 __drizzle_migrations(hash, created_at)로 적용 이력을 본다.
// 이미 스키마가 있는 DB에 baseline을 "실행 없이 적용됨"으로 표시한다.
const sql = neon(process.env.DATABASE_URL!);
const journal = JSON.parse(readFileSync('drizzle/meta/_journal.json', 'utf8')) as {
  entries: { tag: string; when: number }[];
};
await sql`create schema if not exists drizzle`;
await sql`create table if not exists drizzle.__drizzle_migrations (
  id serial primary key, hash text not null, created_at bigint
)`;
for (const e of journal.entries) {
  const body = readFileSync(`drizzle/${e.tag}.sql`, 'utf8');
  const hash = createHash('sha256').update(body).digest('hex');
  const [{ n }] = await sql`select count(*)::int as n from drizzle.__drizzle_migrations where hash = ${hash}`;
  if (n > 0) { console.log(`skip ${e.tag} (already recorded)`); continue; }
  await sql`insert into drizzle.__drizzle_migrations (hash, created_at) values (${hash}, ${e.when})`;
  console.log(`marked ${e.tag}`);
}
```
세 브랜치에 각각 실행:
```powershell
npx dotenv -e .env.local -- npx tsx scripts/mark-migration-applied.mts
npx dotenv -e .env.test  -- npx tsx scripts/mark-migration-applied.mts
# production: Vercel에서 env를 임시로 받아 실행하고 파일은 즉시 삭제 (README 절차)
```

// 프리플라이트 — 하나라도 어긋나면 아무것도 쓰지 않고 중단한다.
const [{ n: alreadyTracked }] = await sql`
  select count(*)::int as n from information_schema.tables
  where table_schema = 'drizzle' and table_name = '__drizzle_migrations'`;
const tables = (await sql`
  select table_name from information_schema.tables
  where table_schema = 'public' order by 1`).map((t) => t.table_name as string);
const EXPECTED = ['account','dues_payments','dues_rounds','groups','ledger_entries','memberships','session','user','verification'];
if (tables.join(',') !== EXPECTED.join(',')) {
  console.log('ABORT — public 스키마가 기대한 베이스라인과 다릅니다:', tables.join(', '));
  process.exit(1);
}
if (alreadyTracked > 0) console.log('note: 이력 테이블이 이미 있습니다 — 중복 기록은 hash로 건너뜁니다.');

  **배포 권한은 CI 한 곳에만 둔다.** 훅이 아니라 `vercel deploy --prod --token`을 쓴다: 훅은 발동 시점의 브랜치 HEAD를 빌드하지만, CLI는 **CI가 `check`·`e2e`로 검증한 바로 그 커밋**을 배포한다. 이로써 "테스트가 빨간 커밋이 프로덕션에 가는" 경로가 닫힌다(Plan 02의 500 사고가 바로 이 계열의 문제였다).
  - Step 6을 머지한 뒤 **첫 배포가 실제로 만들어지는지 CI 로그와 Vercel 배포 목록으로 확인**한다. 자동배포를 껐으므로, CI 배포가 동작하지 않으면 아무도 배포하지 않는 상태가 된다 — 이 확인은 생략할 수 없다.

> **구현 정정 ①(2026-09-15): 배포는 CLI가 아니라 REST API로 한다.** 위 스니펫의 `npx vercel deploy`는 **동작하지 않는다.** 등록된 `VERCEL_TOKEN`은 **프로젝트 스코프** 토큰이어서 `GET /v9/projects/{id}`는 200인데 `GET /v2/user`는 404, `GET /v2/teams`는 403이다. > 1. **멱등성은 출력으로 확인할 수 없다.** `drizzle-kit migrate`는 적용할 것이 없어도 항상 `migrations applied successfully!`를 출력한다("No migrations to apply" 같은 문구는 없다). 멱등 증명은 **`drizzle.__drizzle_migrations`의 행 수**로만 가능하다.
> 2. **Step 2 스니펫의 쓰기 순서가 위험했다.** `create schema` / `create table`을 Step 3의 프리플라이트보다 먼저 실행하게 되어 있어, 잘못된 DB에 실행하면 빈 이력 테이블을 남긴다. **프리플라이트가 어떤 쓰기보다 먼저** 오도록 순서를 바꿨다.
> 3. **`npx tsx`는 불필요하고 설치돼 있지도 않다.** Node 24는 `.mts`의 타입을 스스로 벗겨 실행한다. 게다가 플랜이 쓴 중첩 형태 `npx dotenv -e X -- npx tsx …`는 **Windows에서 실패**한다(`could not determine executable to run`) — 안쪽 `npx`를 빼야 한다.
> 4. 파일 구조표는 `db:migrate:prod`, Step 4는 `db:migrate:test`로 어긋났다 — Step 4를 따랐다(프로덕션은 CI deploy 잡이 담당하므로 로컬 스크립트를 두지 않는 것이 맞다).
> 5. `.gitattributes`에 `*.mts` 규칙이 없었다. 마이그레이션 해시는 **파일 원문 바이트의 sha256**이라 줄바꿈이 흔들리면 플랫폼 간 해시가 달라진다(`*.sql`은 이미 `eol=lf`여서 baseline 해시는 안전했다). `*.mts`를 추가했다.
>
> **리뷰에서 추가로 확인된 사실 — 적용 여부는 해시가 아니라 `created_at`이 가른다:** pg 다이얼렉트(`pg-core/dialect.cjs`)는 이력의 **최신 행 하나**를 읽어 `lastRow.created_at < migration.folderMillis`인 것만 적용한다. 해시는 기록되지만 비교되지 않는다. 따라서 ① 베이스라인을 "적용됨"으로 만드는 핵심은 `created_at = journal.when`이고 ② 혹시 줄바꿈으로 해시가 달라져도 재실행되지는 않는다. 앞으로 같은 작업을 할 때 해시보다 `created_at`을 먼저 확인할 것.
>
> **프리플라이트의 남은 한계(후속):** 테이블 *이름*만 비교한다. 9개가 다 있지만 인덱스나 제약이 하나 빠진 브랜치는 프리플라이트를 통과해 "적용됨"으로 표시되고, 그 빠진 객체는 **영구히 안 들어온다**. `drizzle/meta/0000_snapshot.json`에 제약·인덱스 이름이 있으므로 그것까지 대조하는 것이 강한 형태다. 지금은 세 브랜치가 같은 해시로 확인됐으므로 미룬다.

  id: text('id').primaryKey(),

```markdown
# ADR-003: 정산(엔빵)은 원장에 기록하지 않는다

2026-09-15 · 상태: 승인

## 결정

이벤트 정산(회식비 엔빵 등)의 계산 결과는 `settlements`/`settlement_participants`/`settlement_transfers`에만 저장하고
`ledger_entries`에는 **아무것도 넣지 않는다**. 모임 잔액은 정산에 영향받지 않는다.

## 이유

- 원장은 **모임 돈**의 출입을 기록한다(회비 수입, 모임 지출). 정산은 **멤버 사이의 채무** 정리다 —
  민지가 철수에게 8,000원을 보내는 일은 모임 통장을 지나가지 않는다. 이를 원장에 넣으면
  잔액이 모임 자산을 더 이상 뜻하지 않게 되고, ADR-001이 지키려는 "잔액 = 모임이 가진 돈"이 깨진다.
- 정산을 원장에 넣으면 모든 정산이 합계 0인 엔트리 쌍을 만들어 원장을 소음으로 채운다.
- 모임 통장에서 나간 회식비는 **지출(F3)** 로 따로 기록하면 된다. 그 지출을 참여자끼리 어떻게
  나눴는지가 정산이다 — 두 기록의 관심사가 다르다.

## 결과

- 정산 결과는 **스냅샷**이다. 나중에 명단이나 금액이 바뀌어도 과거 정산은 재계산하지 않는다.
- 정산에는 역분개가 없다. 잘못 만든 정산은 삭제하거나 새로 만든다(원장 불변식과 무관하므로).
- 공개 장부(F5)는 원장을 보여주므로 정산은 기본적으로 포함하지 않는다. 필요하면 별도 섹션으로 둔다.

## 기각한 대안

- **정산을 원장 엔트리로 기록**: 잔액의 의미가 오염된다(위 참조).
- **정산 결과를 저장하지 않고 매번 재계산**: 명단이 바뀌면 과거 정산 결과가 소급 변경돼
  "그때 누가 누구에게 얼마 보냈는지"의 기록이 사라진다.
```

  1. **분배 합계 = 총액** (1원도 사라지지 않는다)
  2. **나머지 배분**: 총액이 인원으로 나누어떨어지지 않으면 1원씩 앞에서부터 더 낸다(누가 더 내는지가 결정적이어야 한다 — 같은 입력에 같은 결과)
  3. **이체 건수**: 채권자가 선결제자 한 명이므로 이체는 n−1건 이하다. **상계(netting)는 하지 않는다** — 채권자가 한 명이면 상계할 것이 없다. 다중 채권자 정산은 v1 범위 밖이며, 그때만 그리디 netting이 필요하다 (Codex IMPORTANT 6 수용 — 원안은 "그리디 최소 이체"라 주장했는데 구현은 단일 선결제자 모델이라 주장이 사실과 달랐다)
  4. **이체 합계 = 채무 합계**, 모든 이체 금액은 양수
  5. **선결제자(payer)는 받는 쪽**이다

```ts
export class SettlementRuleError extends Error {
  constructor(public code: 'INVALID_AMOUNT' | 'NO_PARTICIPANTS' | 'PAYER_NOT_PARTICIPANT') {
    super(code);
  }
}

export type Share = { membershipId: string; amount: number };
export type Transfer = { from: string; to: string; amount: number };

/**
 * 총액을 참여자 수로 나눈다. 나누어떨어지지 않는 나머지는 **앞에서부터 1원씩** 더 낸다 —
 * 무작위로 흘리면 같은 입력에 다른 결과가 나오고, 버리면 합계가 총액과 어긋난다.
 * 분배 합계 = 총액은 이 함수의 불변식이다.
 */
export function splitEvenly(total: number, participantIds: readonly string[]): Share[] {
  if (participantIds.length === 0) throw new SettlementRuleError('NO_PARTICIPANTS');
  if (!Number.isInteger(total) || total <= 0) throw new SettlementRuleError('INVALID_AMOUNT');
  const base = Math.floor(total / participantIds.length);
  let remainder = total - base * participantIds.length;
  return participantIds.map((membershipId) => {
    const extra = remainder > 0 ? 1 : 0;
    remainder -= extra;
    return { membershipId, amount: base + extra };
  });
}

/**
 * 선결제자(payer)가 총액을 이미 냈다는 전제로, 나머지가 payer에게 보낼 이체 목록을 만든다.
 * 한 사람이 냈으므로 채권자는 payer 한 명뿐이라 이체는 최대 n−1건이고, 상계할 것이 없다.
 * (여러 사람이 나눠 낸 정산은 v1 범위 밖 — 그 경우에만 그리디 상계가 필요해진다.)
 */
export function minimalTransfers(
  shares: readonly Share[],
  payerId: string,
  total: number,
): Transfer[] {
  if (shares.length === 0) throw new SettlementRuleError('NO_PARTICIPANTS');
  if (!shares.some((s) => s.membershipId === payerId)) throw new SettlementRuleError('PAYER_NOT_PARTICIPANT');
  if (shares.reduce((n, s) => n + s.amount, 0) !== total) throw new SettlementRuleError('INVALID_AMOUNT');
  return shares
    .filter((s) => s.membershipId !== payerId && s.amount > 0)
    .map((s) => ({ from: s.membershipId, to: payerId, amount: s.amount }));
}
```

import { groupActionClient, assertOwner, ActionError } from './clients';
import { revalidatePath } from 'next/cache';
import { db } from '@/lib/db';
import { memberships, settlements, settlementParticipants, settlementTransfers } from '@/lib/db/schema';
import { splitEvenly, minimalTransfers, SettlementRuleError } from '@/lib/domain/settlement';

export const createSettlement = groupActionClient
  .inputSchema(
    z.object({
      groupId: z.string(),
      title: z.string().min(1).max(50),
      total: z.number().int().positive().max(100_000_000),
      occurredOn: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
      payerMembershipId: z.string(),
      participantMembershipIds: z.array(z.string()).min(1).max(100),
    }),
  )
  .action(async ({ parsedInput, ctx }) => {
    assertOwner(ctx.role);

    // 참여자·선결제자가 모두 이 모임의 멤버인지 — 모임 경계는 여기서 그린다(ADR-002).

    const rows = await db
      .select({ id: memberships.id })
      .from(memberships)
      .where(and(eq(memberships.groupId, ctx.groupId), inArray(memberships.id, ids)));
    if (rows.length !== ids.length) throw new ActionError('NOT_MEMBER');

    let shares, transfers;
    try {
      shares = splitEvenly(parsedInput.total, parsedInput.participantMembershipIds);
      transfers = minimalTransfers(shares, parsedInput.payerMembershipId, parsedInput.total);
    } catch (e) {
      throw e instanceof SettlementRuleError ? new ActionError(e.code) : e;
    }

    const settlementId = crypto.randomUUID();

    const nameById = new Map(
      (await db
        .select({ id: memberships.id, displayName: memberships.displayName })
        .from(memberships)
        .where(and(eq(memberships.groupId, ctx.groupId), inArray(memberships.id, ids)))
      ).map((m) => [m.id, m.displayName]),
    );

    await db.transaction(async (tx) => {
      await tx.insert(settlements).values({
        id: settlementId,
        groupId: ctx.groupId,
        title: parsedInput.title,
        total: parsedInput.total,
        payerMembershipId: parsedInput.payerMembershipId,
        occurredAt: new Date(`${parsedInput.occurredOn}T03:00:00.000Z`), // KST 정오
        createdBy: ctx.userId,
      });
      // 참여자는 전원 기록한다 — 선결제자도, 부담액이 0인 사람도.
      await tx.insert(settlementParticipants).values(
        shares.map((s) => ({
          id: crypto.randomUUID(),
          groupId: ctx.groupId,
          settlementId,
          membershipId: s.membershipId,
          displayNameAtTime: nameById.get(s.membershipId) ?? '(알 수 없음)',
          shareAmount: s.amount,
          isPayer: s.membershipId === parsedInput.payerMembershipId,
        })),
      );
      if (transfers.length > 0) {
        await tx.insert(settlementTransfers).values(
          transfers.map((t) => ({
            id: crypto.randomUUID(),
            groupId: ctx.groupId,
            settlementId,
            fromMembershipId: t.from,
            toMembershipId: t.to,
            amount: t.amount,
          })),
        );
      }
    });
    revalidatePath(`/groups/${ctx.groupId}/settle`);
    return { settlementId };
  });

import { db } from '@/lib/db';
import { groups, ledgerEntries, memberships } from './schema';

/** 공개 장부가 내보내는 모든 것 — 여기에 없는 필드는 절대 노출되지 않는다. */
export type PublicLedger = {
  groupName: string;
  balance: number;
  entries: { id: string; type: string; amount: number; occurredAt: Date; category: string | null; memo: string | null; reversalOf: string | null }[];
  members: { displayName: string; role: string }[];
};

export async function getPublicLedger(token: string): Promise<PublicLedger | null> {
  // 토큰으로 모임을 찾되, 이름만 가져온다 — inviteToken/publicToken은 select에 넣지 않는다.
  const [group] = await db
    .select({ id: groups.id, name: groups.name })
    .from(groups)
    .where(eq(groups.publicToken, token));
  if (!group) return null;

  const [entries, members] = await Promise.all([
    db.select({
      id: ledgerEntries.id, type: ledgerEntries.type, amount: ledgerEntries.amount,
      occurredAt: ledgerEntries.occurredAt, category: ledgerEntries.category,
      memo: ledgerEntries.memo, reversalOf: ledgerEntries.reversalOf,
    }).from(ledgerEntries).where(eq(ledgerEntries.groupId, group.id))
      .orderBy(desc(ledgerEntries.occurredAt), desc(ledgerEntries.createdAt)),
    // 표시 이름과 역할만 — userId·이메일은 select에 없다.
    db.select({ displayName: memberships.displayName, role: memberships.role })
      .from(memberships).where(eq(memberships.groupId, group.id)).orderBy(asc(memberships.joinedAt)),
  ]);

  return {
    groupName: group.name,
    balance: entries.reduce((n, e) => n + e.amount, 0),
    entries,
    members,
  };
}

```ts
import { describe, it, expect } from 'vitest';
import { toCsv } from '@/lib/csv';

describe('toCsv', () => {
  it('헤더와 행을 CRLF로 잇는다', () => {
    expect(toCsv(['a', 'b'], [['1', '2']])).toBe('a,b\r\n1,2');
  });
  it('쉼표·따옴표·줄바꿈이 든 값을 인용한다', () => {
    expect(toCsv(['x'], [['a,b']])).toBe('x\r\n"a,b"');
    expect(toCsv(['x'], [['그는 "네"라고']])).toBe('x\r\n"그는 ""네""라고"');
    expect(toCsv(['x'], [['첫줄\n둘째줄']])).toBe('x\r\n"첫줄\n둘째줄"');
  });
  it('수식 주입을 막는다 — =, +, -, @ 로 시작하면 앞에 홑따옴표', () => {
    expect(toCsv(['x'], [['=1+1']])).toBe("x\r\n\"'=1+1\"");
    expect(toCsv(['x'], [['@SUM(A1)']])).toBe("x\r\n\"'@SUM(A1)\"");
  });
  it('금액은 ASCII 하이픈 음수로 — 스프레드시트가 숫자로 읽어야 한다', () => {
    expect(toCsv(['x'], [['-96000']])).toBe("x\r\n\"'-96000\"");
  });
});
```
**주의:** 마지막 두 케이스는 충돌한다 — `-96000`은 음수 숫자이지 수식이 아니다. 이것은 의도된 함정이며, **해법은 값을 추측하는 것이 아니라 열의 타입을 아는 것**이다 (Codex IMPORTANT 14 수용 — "숫자로 파싱되면 그대로"는 부족하다: 메모에 `-cmd`가 들어오면 그건 텍스트이므로 이스케이프해야 하는데 파싱 규칙으로는 구분되지 않는다).

**채택 설계 — 열 타입을 받는 직렬화기:**
```ts
export type CsvColumn = { header: string; type: 'text' | 'number' };

/** RFC4180 인용 + 스프레드시트 수식 주입 방어. 수식 방어는 text 열에만 적용한다. */
export function toCsv(columns: readonly CsvColumn[], rows: readonly (readonly string[])[]): string;
```
- `number` 열: `String(amount)` 그대로. 음수는 **ASCII 하이픈**(표시용 U+2212는 스프레드시트가 숫자로 읽지 못한다 — Plan 02 리뷰 후속 2). 인용도 접두사도 붙이지 않는다.
- `text` 열: 선행 공백을 제거한 뒤 첫 글자가 `= + - @ \t \r \n` 중 하나면 앞에 `'`를 붙인다. 그 다음 RFC4180 인용(쉼표·따옴표·개행이 있으면 감싸고 내부 `"`는 `""`로).
- **인용만으로는 수식 주입을 막을 수 없다**(Excel은 인용을 벗긴 뒤 평가한다) — 접두사가 방어이고 인용은 파싱을 위한 것이다.

위 테스트의 마지막 두 케이스를 이 설계에 맞게 고쳐 쓴다: `toCsv([{header:'금액',type:'number'}], [['-96000']])` → `금액\r\n-96000`(접두사 없음), `toCsv([{header:'메모',type:'text'}], [['=1+1']])` → `메모\r\n"'=1+1"`. 구현자는 **고친 테스트를 보고**한다.
- [ ] **Step 2: 구현** — 위 설계대로 `lib/csv.ts` 작성.

      { header: '금액', type: 'number' }, { header: '분류', type: 'text' },

    },
  });
}

Task 8 Step 6의 "일부러 유출 버전을 만들어 테스트가 빨개지는지 확인"은 구체적 절차다. UI 태스크의 마크업은 컴포넌트·testid·문구 형식까지 확정했고 className 수준은 기존 화면의 관용구를 따르도록 위임했다.

**3. 타입 일관성** — `Share`/`Transfer`/`SettlementRuleError`(T5 정의 → T6·T7 사용), `splitEvenly`/`minimalTransfers`(T5 → T6 액션·T7 미리보기), `PublicLedger`/`getPublicLedger`(T8 → T8 화면), `toCsv`(T9 → T9 라우트), `getAllEntries`(T9 Step 3에서 정의·사용), `Amount tone`(T7 Step 1 정의 → T7·T8 사용), `accountLabel`(T10 → T10 문구·T10 Step 6 누출 테스트). 스키마 컬럼은 glossary의 snake_case 규칙을 따르고 TS는 camelCase로 노출한다.

**4. 위험 순서** — 가장 위험한 것을 가장 먼저 두지 않았다: T1(파이프라인)·T2(FK)·T3(테스트)은 **기반**이라 앞이고, T8(공개 장부)이 진짜 위험인데 중간이다. 의도적이다 — T2의 복합 FK와 T3의 자동 인가 테스트가 T8의 안전망이므로 먼저 있어야 한다. T8은 그 자체로도 유출 테스트를 요구한다.
