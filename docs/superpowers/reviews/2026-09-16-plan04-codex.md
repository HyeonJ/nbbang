1. **BLOCKER — `/g/[token]/page.tsx`에서 429 + `Retry-After`를 낼 수 있다는 전제가 틀림**

   **수정:** 최소한 ADR/처리방침에 “내부 불변 식별자는 보존된다”고 명시하거나, 정말 익명화를 원하면 `created_by`를 nullable/tombstone 사용자로 바꾸는 별도 설계를 해야 한다.

## BLOCKER

**1. 레이트 리밋 테스트가 요구하는 헤더 스푸핑이 곧 우회 경로다**  
`clientIp`가 `x-forwarded-for` 첫 항목을 신뢰하고, e2e도 IP 분리를 위해 그 헤더를 직접 넣는다. 이 구조는 “테스트에서 임의 IP를 만들 수 있다”와 “클라이언트가 IP를 속일 수 없다”가 동시에 참이어야 하는데, 계획은 그 신뢰 경계를 증명하지 않는다. Vercel이 해당 헤더를 항상 덮어쓰는지, append인지, 원본 클라이언트 값을 보존하는지 확인 없이 구현하면 공격자가 `x-forwarded-for`를 바꿔 버킷을 무한 회피할 수 있다.  
**수정:** 배포 플랫폼이 보장하는 원격 IP 헤더를 문서로 확인하고, 사용자 제공 헤더가 섞이지 않음을 테스트/운영 메모에 남겨라. 불확실하면 `x-forwarded-for` 직접 신뢰를 중단하고 플랫폼 전용 헤더 또는 edge/middleware 레벨에서만 처리하라.

**2. `checkRateLimit` fail-open 테스트 설계가 현재 함수 시그니처와 맞지 않는다**  
계획은 “존재하지 않는 테이블을 보게 만든 핸들을 주입”하라고 하지만 `checkRateLimit(bucket, limit, windowSeconds)`는 DB 핸들을 받지 않는다. 현재 설계대로면 통합 테스트에서 의도적으로 실패 DB를 주입할 수 없다. 모듈 mock을 쓰면 “실제 DB 왕복”이라는 Step 5의 전제와 충돌한다.  
**수정:** `checkRateLimit` 내부 구현을 `createRateLimiter(dbLike)` 형태로 분리하거나, 테스트 전용으로 SQL 실행 함수를 주입할 수 있게 하라. fail-open은 핵심 정책이므로 테스트 가능성이 설계에 반영돼야 한다.

**3. 모임 삭제는 동시 쓰기와 충돌할 수 있다**  
삭제 순서를 맞춰도, 삭제 트랜잭션 중 다른 서버 액션이 같은 `group_id`로 `dues_payments`나 `ledger_entries`를 새로 넣으면 마지막 `groups` 삭제가 FK 23503으로 실패하거나 대기/교착 상태가 생길 수 있다. 실사용자 0명이어도 삭제 기능은 파괴적이라 실패 시 UX와 데이터 상태가 중요하다.  
**수정:** 삭제 트랜잭션 시작 시 `groups` 행을 `SELECT ... FOR UPDATE`로 잠그고, 가능한 한 모든 쓰기가 FK의 `groups` 참조를 통해 같은 락과 충돌하게 만들어라. 실패 시 전체 롤백과 재시도 가능 메시지도 테스트해야 한다.

**4. `settlement_participants.display_name_at_time` 익명화 키가 명시되지 않았다**  
계획은 정산 참여자 이름을 `'탈퇴한 멤버'`로 바꾼다고 하지만, 어떤 컬럼으로 “이 탈퇴자”의 참여자 행을 찾는지 없다. `membership_id` 같은 안정 키가 있으면 괜찮지만, 표시명 문자열 매칭이면 같은 이름의 다른 사람을 지우거나, 이름 변경 이력이 있는 사용자를 놓친다. 이는 ADR-003 데이터 보존과 개인정보 파기 둘 다 실패한다.  
**수정:** `settlement_participants`가 반드시 `membership_id` 또는 동등한 FK를 갖는지 확인하고, 그 키로만 익명화하라. 없다면 스키마 변경 없이 이 요구사항은 정확히 구현할 수 없다.

**5. “원래 이메일·표시명이 DB 어디에도 남지 않는다”는 테스트가 현실적으로 거짓일 수 있다**  
이 서비스에는 `ledger_entries.memo`, `groups.accountLabel`, 정산 제목/메모류처럼 사용자가 자유 텍스트를 넣는 영역이 있다. 사용자가 자기 이메일이나 이름을 메모에 썼다면 구조화된 사용자 컬럼만 익명화해도 DB 검색에는 그대로 남는다. 계획의 테스트가 “알려진 컬럼 전수 확인”이라고만 되어 있으면 구현자가 어디까지 지워야 하는지 불명확하다.  
**수정:** 삭제 범위를 “계정/프로필/멤버십/정산 참여자 스냅샷의 구조화된 식별자”로 좁혀 명시하라. 자유 텍스트까지 파기하려면 별도 PII 탐지·수정 기능이 필요하며, 이 플랜 범위를 크게 넘는다.

## IMPORTANT

**6. 레이트 리밋 bucket 값이 검증·정규화되지 않는다**  
`g:<ip>`에 원본 헤더 값을 그대로 붙이면 IPv6 표기 흔들림, 포트 포함 값, 비정상적으로 긴 문자열, 쉼표/공백 변형이 그대로 PK에 들어간다. 이건 우회와 DB 인덱스 팽창을 동시에 만든다.  
**수정:** `clientIp`는 실제 IP 파서로 IPv4/IPv6만 허용하고 정규화해야 한다. 유효하지 않으면 `null` 또는 차단 중 하나로 일관되게 처리하라. 저장값은 `g:${hmac(ip)}`처럼 길이가 고정된 값이 낫다.

**7. `Date.now()`로 `Retry-After`를 계산하면 DB 시계와 앱 시계 차이에 취약하다**  
윈도 시작은 DB의 `now()`로 저장하고, elapsed는 앱 서버의 `Date.now()`로 계산한다. 서버리스 환경에서 시계 차이가 크지는 않더라도 테스트와 운영에서 음수/과대 retry가 나올 수 있다.  
**수정:** SQL `returning count, greatest(1, ceil(extract(epoch from (window_start + interval ... - now())))) as retry_after_seconds`처럼 DB 안에서 계산하라.

**8. `CRON_SECRET` 미설정 케이스가 위험하다**  
계획은 “없거나 다르면 401”이라고 하지만 구현자가 `auth === \`Bearer ${process.env.CRON_SECRET}\``만 쓰면 환경변수 미설정 시 `Bearer undefined`가 통과할 수 있다.  
**수정:** `const secret = process.env.CRON_SECRET; if (!secret) return 500/401`를 먼저 검사하라. 테스트도 “env 없음”, “헤더 없음”, “틀린 값”, “맞는 값”을 분리해야 한다.

**9. `vercel.json` 생성은 기존 설정을 덮을 수 있다**  
파일 구조에 “Create: `vercel.json`”라고 되어 있다. 레포에 이미 rewrites, headers, build 설정이 있으면 새 파일 생성/덮어쓰기로 배포 설정을 망가뜨릴 수 있다.  
**수정:** “없으면 생성, 있으면 crons 배열만 병합”으로 바꾸고, 기존 키 보존 테스트 또는 리뷰 체크를 넣어라.

**10. 삭제 순서 테스트의 “12개 테이블”은 쉽게 낡는다**  
“12개 테이블 전부 0”은 지금은 좋아 보이지만, 테이블이 추가되면 테스트와 삭제 목록이 동시에 누락될 수 있다. 그러면 잘못된 구현도 초록이 된다.  
**수정:** `lib/db/delete.ts`의 삭제 대상 목록을 테스트에서 읽어 검증하거나, DB FK 메타데이터로 `groups`를 직접/간접 참조하는 테이블을 찾아 삭제 목록과 대조하라.

**11. 모임 삭제 이름 확인은 트랜잭션 안의 현재 이름으로 해야 한다**  
계획은 서버에서 확인한다고만 한다. 액션 시작 전에 읽은 이름과 삭제 직전 이름이 다르면, 사용자는 다른 이름의 모임을 삭제할 수 있다.  
**수정:** 삭제 트랜잭션 안에서 `groups` 행을 잠근 뒤 그 시점의 `name`과 입력값을 비교하라. 틀리면 아무 child row도 삭제하지 않고 `NAME_MISMATCH`로 종료해야 한다.

**12. 탈퇴 중 동시 요청이 새 원장/정산을 만들 수 있다**  
세션 삭제는 이후 요청을 막지만, 이미 인증을 통과한 병렬 요청은 탈퇴 트랜잭션과 겹칠 수 있다. 그러면 `deletedAt`이 찍힌 사용자로 새 `ledger_entries.created_by`가 생길 수 있다.  
**수정:** 탈퇴 트랜잭션에서 `user` 행을 잠그고, 모든 쓰기 액션의 공통 인가 계층에서 `deletedAt is null`을 쓰기 직전에도 확인하라. 가능하면 integration으로 “탈퇴와 원장 생성 동시 실행”을 한 번 고정하라.

**13. Better Auth 관련 파기 범위가 `account`/`session`에 한정되어 있다**  
Better Auth 구성에 따라 verification token, password reset, passkey, two-factor, oauth state 같은 테이블이 있을 수 있다. 계획은 “account와 session 삭제”만 명시해서 이메일이나 credential 파편이 남을 위험이 있다.  
**수정:** 실제 `schema.ts`의 Better Auth 테이블을 전수 확인하고, 사용자 식별자나 credential을 가진 테이블을 ADR-004 표와 테스트에 모두 포함하라.

**14. 로그인 차단 위치가 모호하다**  
“로그인 경로에서 `deletedAt` 사용자를 거부”라고 하지만, 이메일을 `deleted-uuid@deleted.invalid`로 바꾸고 `account`도 지우면 일반 로그인은 이미 실패한다. 문제는 기존 세션 검증, OAuth 재연결, 내부 auth helper가 deleted user를 어떻게 취급하느냐다.  
**수정:** Better Auth hook/adapter 레벨에서 `deletedAt` 사용자가 session user로 반환되지 않게 하라. 앱 레벨 middleware만으로 막으면 서버 액션 auth helper와 불일치할 수 있다.

**15. 개인정보처리방침의 “문의: GitHub 이슈”는 개인정보 요청 경로로 부적절하다**  
삭제·열람 요청을 GitHub public issue로 유도하면 사용자가 이메일, 모임명, 장부 내용을 공개 이슈에 적을 수 있다. 전용 이메일을 “나중”으로 미루는 것은 실사용자 수 0명 단계라도 개인정보처리방침의 완성도를 떨어뜨린다.  
**수정:** 최소한 비공개 연락 채널을 만들거나, GitHub 이슈에는 개인정보를 쓰지 말라는 경고와 별도 연락 방법을 제공하라.

**16. 공개 장부 링크의 개인정보 영향 고지가 부족하다**  
공개 장부는 로그인 없이 링크 보유자가 장부를 본다. 처리방침에 한 줄 고지는 있지만, 총무가 공유하기 전에 멤버 이름·지출 내역이 링크 수신자에게 보인다는 제품 내 경고가 계획에 없다.  
**수정:** 공개 링크 발급/재발급 화면에 노출 범위와 재발급 효과를 명시하라. 공개 장부 footer 링크만으로는 동의·인지 흐름이 약하다.

**17. 프로덕션 스모크에서 “12개 테이블 전부 0행”은 위험한 운영 절차다**  
프로덕션 DB에서 테이블 전체 0행을 확인하는 절차는 실사용자 0명 전제에만 맞다. 첫 사용자 이후 같은 문서가 남아 있으면 사고 절차가 된다.  
**수정:** 스모크 전용 테스트 계정/그룹 ID 범위만 확인하도록 바꾸고, “실사용자 유입 전 1회성”이라고 명시하라.

## MINOR

**18. 고정 윈도는 경계에서 최대 2배 burst를 허용한다**  
60회/분이면 59초와 60초 경계에 걸쳐 짧은 시간에 120회 가까이 허용될 수 있다. 비용 방어 목적이면 치명적이지 않지만, “반복 긁기” 방어로는 한계가 있다.  
**수정:** 현 단계에서는 고정 윈도를 유지해도 된다. 다만 주석에 “경계 burst 허용”을 명시하고, 운영 로그에서 문제가 보이면 sliding window 또는 token bucket으로 바꾸는 기준을 남겨라.

**19. IP당 60회/분은 공유망 사용자에게 거칠 수 있다**  
동아리방, 회사, 학교 NAT 뒤에서 여러 명이 같은 공개 링크를 열면 한 IP로 합산된다. 계획은 토큰당 제한을 피하려다 정상 공유 IP를 막을 수 있다.  
**수정:** 기본값을 환경변수로 빼고, 429 화면에 잠시 후 재시도 안내를 명확히 넣어라. 운영 중 조정 가능해야 한다.

**20. 처리방침 수집 항목에 쿠키/세션이 빠졌다**  
Better Auth를 쓰면 세션 쿠키와 session table의 토큰/만료시각이 서비스 제공에 쓰인다. “비밀번호 해시”만 쓰면 인증 관련 개인정보가 축소 기재된다.  
**수정:** 세션 쿠키, 접속 로그/IP, 인증 제공자 계정 식별자를 실제 사용 범위에 맞춰 추가하라.

**21. “외부 호스트 요청 0건” 테스트는 privacy 링크 자체보다 페이지 구현을 봐야 한다**  
단순 내부 링크는 외부 요청을 만들지 않는다. 깨질 가능성은 privacy 페이지나 footer가 외부 폰트, GitHub 링크 preview, 원격 이미지 등을 넣을 때다.  
**수정:** 공개 장부에서 링크 클릭 후 `/privacy`까지 포함해 network assertion을 유지하라. GitHub 문의 링크는 클릭하지 않는 한 요청이 없어야 한다.

**22. 변이 증명 절차가 수동 보고에 의존한다**  
“주석 처리 → 빨개짐 관측 → 되돌림 → 실패 메시지 보고”는 좋은 습관이지만, 커밋 가능한 증거가 남지 않는다.  
**수정:** 핵심 방어는 가능하면 테스트 이름과 fixture로 의미가 드러나게 하고, 수동 변이 결과는 구현 노트에 짧게 남겨라. 모든 항목에 과도하게 적용하면 속도만 떨어진다.

**23. 총무 위임 제외는 합리적이지만 UX 문구가 중요하다**  
“총무는 탈퇴할 수 없다”는 정책은 v1에서 가능하다. 다만 사용자는 계정을 지우려다 모임 삭제를 강제당하는 것으로 느낄 수 있다.  
**수정:** 에러 메시지는 “소유한 모임을 먼저 삭제하거나, 향후 총무 위임 기능이 필요하다”처럼 이유를 설명해야 한다. ADR에도 제품상 미결로 남겨라.

**24. “법적 형식을 갖춘 정적 페이지”라는 표현이 과하다**  
Vercel/Neon 리전만 확인한다고 법적 형식이 완성되지는 않는다. 개인정보처리자, 문의처, 보관기간, 국외 이전 국가·일시·항목, 이용자 권리 행사 방법 등이 빠지면 형식상 허점이 남는다.  
**수정:** 법률 자문 없이 “법적 형식”이라고 단정하지 말고, “서비스 정책 초안”으로 표현하거나 필수 항목 체크리스트를 추가하라.

## BLOCKER

**1. 레이트 리밋 테스트가 요구하는 헤더 스푸핑이 곧 우회 경로다**  
`clientIp`가 `x-forwarded-for` 첫 항목을 신뢰하고, e2e도 IP 분리를 위해 그 헤더를 직접 넣는다. 이 구조는 “테스트에서 임의 IP를 만들 수 있다”와 “클라이언트가 IP를 속일 수 없다”가 동시에 참이어야 하는데, 계획은 그 신뢰 경계를 증명하지 않는다. Vercel이 해당 헤더를 항상 덮어쓰는지, append인지, 원본 클라이언트 값을 보존하는지 확인 없이 구현하면 공격자가 `x-forwarded-for`를 바꿔 버킷을 무한 회피할 수 있다.  
**수정:** 배포 플랫폼이 보장하는 원격 IP 헤더를 문서로 확인하고, 사용자 제공 헤더가 섞이지 않음을 테스트/운영 메모에 남겨라. 불확실하면 `x-forwarded-for` 직접 신뢰를 중단하고 플랫폼 전용 헤더 또는 edge/middleware 레벨에서만 처리하라.

**2. `checkRateLimit` fail-open 테스트 설계가 현재 함수 시그니처와 맞지 않는다**  
계획은 “존재하지 않는 테이블을 보게 만든 핸들을 주입”하라고 하지만 `checkRateLimit(bucket, limit, windowSeconds)`는 DB 핸들을 받지 않는다. 현재 설계대로면 통합 테스트에서 의도적으로 실패 DB를 주입할 수 없다. 모듈 mock을 쓰면 “실제 DB 왕복”이라는 Step 5의 전제와 충돌한다.  
**수정:** `checkRateLimit` 내부 구현을 `createRateLimiter(dbLike)` 형태로 분리하거나, 테스트 전용으로 SQL 실행 함수를 주입할 수 있게 하라. fail-open은 핵심 정책이므로 테스트 가능성이 설계에 반영돼야 한다.

**3. 모임 삭제는 동시 쓰기와 충돌할 수 있다**  
삭제 순서를 맞춰도, 삭제 트랜잭션 중 다른 서버 액션이 같은 `group_id`로 `dues_payments`나 `ledger_entries`를 새로 넣으면 마지막 `groups` 삭제가 FK 23503으로 실패하거나 대기/교착 상태가 생길 수 있다. 실사용자 0명이어도 삭제 기능은 파괴적이라 실패 시 UX와 데이터 상태가 중요하다.  
**수정:** 삭제 트랜잭션 시작 시 `groups` 행을 `SELECT ... FOR UPDATE`로 잠그고, 가능한 한 모든 쓰기가 FK의 `groups` 참조를 통해 같은 락과 충돌하게 만들어라. 실패 시 전체 롤백과 재시도 가능 메시지도 테스트해야 한다.

**4. `settlement_participants.display_name_at_time` 익명화 키가 명시되지 않았다**  
계획은 정산 참여자 이름을 `'탈퇴한 멤버'`로 바꾼다고 하지만, 어떤 컬럼으로 “이 탈퇴자”의 참여자 행을 찾는지 없다. `membership_id` 같은 안정 키가 있으면 괜찮지만, 표시명 문자열 매칭이면 같은 이름의 다른 사람을 지우거나, 이름 변경 이력이 있는 사용자를 놓친다. 이는 ADR-003 데이터 보존과 개인정보 파기 둘 다 실패한다.  
**수정:** `settlement_participants`가 반드시 `membership_id` 또는 동등한 FK를 갖는지 확인하고, 그 키로만 익명화하라. 없다면 스키마 변경 없이 이 요구사항은 정확히 구현할 수 없다.

**5. “원래 이메일·표시명이 DB 어디에도 남지 않는다”는 테스트가 현실적으로 거짓일 수 있다**  
이 서비스에는 `ledger_entries.memo`, `groups.accountLabel`, 정산 제목/메모류처럼 사용자가 자유 텍스트를 넣는 영역이 있다. 사용자가 자기 이메일이나 이름을 메모에 썼다면 구조화된 사용자 컬럼만 익명화해도 DB 검색에는 그대로 남는다. 계획의 테스트가 “알려진 컬럼 전수 확인”이라고만 되어 있으면 구현자가 어디까지 지워야 하는지 불명확하다.  
**수정:** 삭제 범위를 “계정/프로필/멤버십/정산 참여자 스냅샷의 구조화된 식별자”로 좁혀 명시하라. 자유 텍스트까지 파기하려면 별도 PII 탐지·수정 기능이 필요하며, 이 플랜 범위를 크게 넘는다.

## IMPORTANT

**6. 레이트 리밋 bucket 값이 검증·정규화되지 않는다**  
`g:<ip>`에 원본 헤더 값을 그대로 붙이면 IPv6 표기 흔들림, 포트 포함 값, 비정상적으로 긴 문자열, 쉼표/공백 변형이 그대로 PK에 들어간다. 이건 우회와 DB 인덱스 팽창을 동시에 만든다.  
**수정:** `clientIp`는 실제 IP 파서로 IPv4/IPv6만 허용하고 정규화해야 한다. 유효하지 않으면 `null` 또는 차단 중 하나로 일관되게 처리하라. 저장값은 `g:${hmac(ip)}`처럼 길이가 고정된 값이 낫다.

**7. `Date.now()`로 `Retry-After`를 계산하면 DB 시계와 앱 시계 차이에 취약하다**  
윈도 시작은 DB의 `now()`로 저장하고, elapsed는 앱 서버의 `Date.now()`로 계산한다. 서버리스 환경에서 시계 차이가 크지는 않더라도 테스트와 운영에서 음수/과대 retry가 나올 수 있다.  
**수정:** SQL `returning count, greatest(1, ceil(extract(epoch from (window_start + interval ... - now())))) as retry_after_seconds`처럼 DB 안에서 계산하라.

**8. `CRON_SECRET` 미설정 케이스가 위험하다**  
계획은 “없거나 다르면 401”이라고 하지만 구현자가 `auth === \`Bearer ${process.env.CRON_SECRET}\``만 쓰면 환경변수 미설정 시 `Bearer undefined`가 통과할 수 있다.  
**수정:** `const secret = process.env.CRON_SECRET; if (!secret) return 500/401`를 먼저 검사하라. 테스트도 “env 없음”, “헤더 없음”, “틀린 값”, “맞는 값”을 분리해야 한다.

**9. `vercel.json` 생성은 기존 설정을 덮을 수 있다**  
파일 구조에 “Create: `vercel.json`”라고 되어 있다. 레포에 이미 rewrites, headers, build 설정이 있으면 새 파일 생성/덮어쓰기로 배포 설정을 망가뜨릴 수 있다.  
**수정:** “없으면 생성, 있으면 crons 배열만 병합”으로 바꾸고, 기존 키 보존 테스트 또는 리뷰 체크를 넣어라.

**10. 삭제 순서 테스트의 “12개 테이블”은 쉽게 낡는다**  
“12개 테이블 전부 0”은 지금은 좋아 보이지만, 테이블이 추가되면 테스트와 삭제 목록이 동시에 누락될 수 있다. 그러면 잘못된 구현도 초록이 된다.  
**수정:** `lib/db/delete.ts`의 삭제 대상 목록을 테스트에서 읽어 검증하거나, DB FK 메타데이터로 `groups`를 직접/간접 참조하는 테이블을 찾아 삭제 목록과 대조하라.

**11. 모임 삭제 이름 확인은 트랜잭션 안의 현재 이름으로 해야 한다**  
계획은 서버에서 확인한다고만 한다. 액션 시작 전에 읽은 이름과 삭제 직전 이름이 다르면, 사용자는 다른 이름의 모임을 삭제할 수 있다.  
**수정:** 삭제 트랜잭션 안에서 `groups` 행을 잠근 뒤 그 시점의 `name`과 입력값을 비교하라. 틀리면 아무 child row도 삭제하지 않고 `NAME_MISMATCH`로 종료해야 한다.

**12. 탈퇴 중 동시 요청이 새 원장/정산을 만들 수 있다**  
세션 삭제는 이후 요청을 막지만, 이미 인증을 통과한 병렬 요청은 탈퇴 트랜잭션과 겹칠 수 있다. 그러면 `deletedAt`이 찍힌 사용자로 새 `ledger_entries.created_by`가 생길 수 있다.  
**수정:** 탈퇴 트랜잭션에서 `user` 행을 잠그고, 모든 쓰기 액션의 공통 인가 계층에서 `deletedAt is null`을 쓰기 직전에도 확인하라. 가능하면 integration으로 “탈퇴와 원장 생성 동시 실행”을 한 번 고정하라.

**13. Better Auth 관련 파기 범위가 `account`/`session`에 한정되어 있다**  
Better Auth 구성에 따라 verification token, password reset, passkey, two-factor, oauth state 같은 테이블이 있을 수 있다. 계획은 “account와 session 삭제”만 명시해서 이메일이나 credential 파편이 남을 위험이 있다.  
**수정:** 실제 `schema.ts`의 Better Auth 테이블을 전수 확인하고, 사용자 식별자나 credential을 가진 테이블을 ADR-004 표와 테스트에 모두 포함하라.

**14. 로그인 차단 위치가 모호하다**  
“로그인 경로에서 `deletedAt` 사용자를 거부”라고 하지만, 이메일을 `deleted-uuid@deleted.invalid`로 바꾸고 `account`도 지우면 일반 로그인은 이미 실패한다. 문제는 기존 세션 검증, OAuth 재연결, 내부 auth helper가 deleted user를 어떻게 취급하느냐다.  
**수정:** Better Auth hook/adapter 레벨에서 `deletedAt` 사용자가 session user로 반환되지 않게 하라. 앱 레벨 middleware만으로 막으면 서버 액션 auth helper와 불일치할 수 있다.

**15. 개인정보처리방침의 “문의: GitHub 이슈”는 개인정보 요청 경로로 부적절하다**  
삭제·열람 요청을 GitHub public issue로 유도하면 사용자가 이메일, 모임명, 장부 내용을 공개 이슈에 적을 수 있다. 전용 이메일을 “나중”으로 미루는 것은 실사용자 수 0명 단계라도 개인정보처리방침의 완성도를 떨어뜨린다.  
**수정:** 최소한 비공개 연락 채널을 만들거나, GitHub 이슈에는 개인정보를 쓰지 말라는 경고와 별도 연락 방법을 제공하라.

**16. 공개 장부 링크의 개인정보 영향 고지가 부족하다**  
공개 장부는 로그인 없이 링크 보유자가 장부를 본다. 처리방침에 한 줄 고지는 있지만, 총무가 공유하기 전에 멤버 이름·지출 내역이 링크 수신자에게 보인다는 제품 내 경고가 계획에 없다.  
**수정:** 공개 링크 발급/재발급 화면에 노출 범위와 재발급 효과를 명시하라. 공개 장부 footer 링크만으로는 동의·인지 흐름이 약하다.

**17. 프로덕션 스모크에서 “12개 테이블 전부 0행”은 위험한 운영 절차다**  
프로덕션 DB에서 테이블 전체 0행을 확인하는 절차는 실사용자 0명 전제에만 맞다. 첫 사용자 이후 같은 문서가 남아 있으면 사고 절차가 된다.  
**수정:** 스모크 전용 테스트 계정/그룹 ID 범위만 확인하도록 바꾸고, “실사용자 유입 전 1회성”이라고 명시하라.

## MINOR

**18. 고정 윈도는 경계에서 최대 2배 burst를 허용한다**  
60회/분이면 59초와 60초 경계에 걸쳐 짧은 시간에 120회 가까이 허용될 수 있다. 비용 방어 목적이면 치명적이지 않지만, “반복 긁기” 방어로는 한계가 있다.  
**수정:** 현 단계에서는 고정 윈도를 유지해도 된다. 다만 주석에 “경계 burst 허용”을 명시하고, 운영 로그에서 문제가 보이면 sliding window 또는 token bucket으로 바꾸는 기준을 남겨라.

**19. IP당 60회/분은 공유망 사용자에게 거칠 수 있다**  
동아리방, 회사, 학교 NAT 뒤에서 여러 명이 같은 공개 링크를 열면 한 IP로 합산된다. 계획은 토큰당 제한을 피하려다 정상 공유 IP를 막을 수 있다.  
**수정:** 기본값을 환경변수로 빼고, 429 화면에 잠시 후 재시도 안내를 명확히 넣어라. 운영 중 조정 가능해야 한다.

**20. 처리방침 수집 항목에 쿠키/세션이 빠졌다**  
Better Auth를 쓰면 세션 쿠키와 session table의 토큰/만료시각이 서비스 제공에 쓰인다. “비밀번호 해시”만 쓰면 인증 관련 개인정보가 축소 기재된다.  
**수정:** 세션 쿠키, 접속 로그/IP, 인증 제공자 계정 식별자를 실제 사용 범위에 맞춰 추가하라.

**21. “외부 호스트 요청 0건” 테스트는 privacy 링크 자체보다 페이지 구현을 봐야 한다**  
단순 내부 링크는 외부 요청을 만들지 않는다. 깨질 가능성은 privacy 페이지나 footer가 외부 폰트, GitHub 링크 preview, 원격 이미지 등을 넣을 때다.  
**수정:** 공개 장부에서 링크 클릭 후 `/privacy`까지 포함해 network assertion을 유지하라. GitHub 문의 링크는 클릭하지 않는 한 요청이 없어야 한다.

**22. 변이 증명 절차가 수동 보고에 의존한다**  
“주석 처리 → 빨개짐 관측 → 되돌림 → 실패 메시지 보고”는 좋은 습관이지만, 커밋 가능한 증거가 남지 않는다.  
**수정:** 핵심 방어는 가능하면 테스트 이름과 fixture로 의미가 드러나게 하고, 수동 변이 결과는 구현 노트에 짧게 남겨라. 모든 항목에 과도하게 적용하면 속도만 떨어진다.

**23. 총무 위임 제외는 합리적이지만 UX 문구가 중요하다**  
“총무는 탈퇴할 수 없다”는 정책은 v1에서 가능하다. 다만 사용자는 계정을 지우려다 모임 삭제를 강제당하는 것으로 느낄 수 있다.  
**수정:** 에러 메시지는 “소유한 모임을 먼저 삭제하거나, 향후 총무 위임 기능이 필요하다”처럼 이유를 설명해야 한다. ADR에도 제품상 미결로 남겨라.

**24. “법적 형식을 갖춘 정적 페이지”라는 표현이 과하다**  
Vercel/Neon 리전만 확인한다고 법적 형식이 완성되지는 않는다. 개인정보처리자, 문의처, 보관기간, 국외 이전 국가·일시·항목, 이용자 권리 행사 방법 등이 빠지면 형식상 허점이 남는다.  
**수정:** 법률 자문 없이 “법적 형식”이라고 단정하지 말고, “서비스 정책 초안”으로 표현하거나 필수 항목 체크리스트를 추가하라.
